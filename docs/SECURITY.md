# Безопасность и обработка данных

## Сетевые запросы и preview

- Preview HTTP-сервер расширения слушает `127.0.0.1` на временном порту.
- **Проверка Host.** Запросы (включая WebSocket-upgrade) принимаются только с `Host: 127.0.0.1:<порт>`, `localhost:<порт>` или `[::1]:<порт>`; всё остальное — 403. Это закрывает DNS rebinding и использование preview-хоста как открытого прокси чужой страницей. Токен-авторизация не используется намеренно: страница приложения — кросс-сайтовый iframe, и `SameSite`-политики браузера не доставят token-cookie её запросам; Host-проверка закрывает основной вектор (rebinding), а защита от «чужого процесса на той же машине» обеспечивается случайным портом, который живёт только пока открыт preview.
- **Файлы проекта.** Маршрут `/project/` не отдаёт `.env`, `.env.*`, ничего внутри `.git/` и `node_modules/` (кроме symlink-jail выше).
- **SSRF-гейт.** Все upstream-адреса — явный proxy-маршрут, Referer-fallback, sticky dev target и WebSocket upgrade — проходят единую проверку (`src/infrastructure/preview/upstream-validation.ts`): только HTTP/HTTPS, без userinfo-креденшелов (`http://user@host/`), только loopback. Разрешены `localhost`, поддомены `.localhost`, `127.0.0.0/8`, `::1`, IPv4-mapped loopback `::ffff:127.x.x.x` и `0.0.0.0`. Приватные сети (`10.x`, `172.16/12`, `192.168/16`), link-local и cloud metadata (`169.254.169.254`), multicast и любые внешние хосты отклоняются с 403 **до** открытия сокета. Dev-репликаторы вида `localtest.me` также отклоняются: имя, которое «обычно» резолвится в loopback, остаётся публичной DNS-записью. Скачивание dev source maps (`sourceMappingURL` в CSS) дополнительно ограничено: только loopback-URL без редиректов (`redirect: "error"`).
- Redirect повторно проходит гейт: proxy работает с `redirect: manual`, каждый hop выполняется браузером через preview host и валидируется заново. Cross-origin Location на **loopback**-адрес переписывается в путь `/proxy/http/...`, поэтому браузер не уходит directly на внешний URL. Location на **внешний (не loopback)** адрес остаётся без изменений: браузер открывает его нативно внутри preview-фрейма (так работают OAuth-провайдеры и внешние SSO), а серверный SSRF-гейт при этом не участвует — запрос minует preview host. После внешней авторизации сессия возвращается на локальный origin приложения.
- Проверка host выполняется по hostname, уже нормализованному URL-парсером (WHATWG), поэтому альтернативные IPv4-записи (десятичный `2130706433`, hex `0x7f000001`) приводятся к каноническому виду до сравнения и не обходят гейт.
- Запросы iframe к активному localhost-серверу проксируются локальным процессом расширения. Браузерные cookies и необходимые app-router/server-action заголовки передаются upstream.
- `Domain` из ответа `Set-Cookie` удаляется, `Path` приводится к `/`, остальные атрибуты cookies сохраняются. Это нужно, чтобы локальная preview-сессия работала между маршрутами. Cookies обрабатывает браузер на временном локальном origin и preview-прокси; Design Studio не использует их для внешних сервисов.
- Серверный cookie jar: preview-хост дополнительно хранит cookies приложения собственной сессии и сам подставляет их в каждый проксированный запрос. Jar **ключуется по upstream-origin**: cookie из ответа `127.0.0.1:3000` не подставляется в запрос к `localhost:4000`, поэтому сессии одного локального приложения не утекают в другое через `/proxy/`. Jar чистится при смене dev-цели, по `Max-Age=0`/истечении `Expires`. Cookies не покидают локальный процесс расширения.
- Контент, прочитанный со страницы приложения (текст, классы, атрибуты, CSS-правила, сниппеты), вставляется в промпт ИИ как **недоверенные данные**: переводы строк внутри значений экранируются (нельзя подделать строку «Пожелание пользователя»), а весь блок данных ограждён явными маркерами `PAGE DATA — START/END` с указанием не выполнять инструкции, найденные внутри.
- Размер тела upstream-запроса ограничен 10 МБ, ответа — 20 МБ, таймаут ответа — 30 секунд.
- Для iframe preview удаляет некоторые response headers проекта, которые блокируют встраивание или вмешиваются в проксирование (в том числе `X-Frame-Options` и CSP response headers). Исходные конфигурационные файлы проекта не меняются. Поэтому используйте режим с доверенным локальным проектом; содержимое страниц проекта исполняется в iframe.

## Файлы workspace

- Проектные файлы отдаёт только локальный HTTP-хост и ограничивает пути корнем workspace. Проверка каноническая: и лексическое ограничение (`path.relative`), и `fs.realpath` самой глубокой существующей директории-предка. Символическая ссылка или junction внутри workspace, ведущая наружу, отклоняется с 403.
- Поиск компонентов и CSS идёт только в открытом workspace. Для копирования исходника допускаются файлы `.tsx`, `.jsx`, `.ts`, `.js`, `.mts`, `.mjs`, `.mdx` размером не более 300 КБ.
- CSS сохраняется через VS Code `WorkspaceEdit`, только если найдено одно однозначное правило. При неопределённом/множественном совпадении запись не производится.

## Буфер обмена и ИИ

- Сгенерированная инструкция и исходник компонента копируются в системный буфер только по нажатию пользователя соответствующей кнопки.
- Расширение не вызывает MCP, агентские расширения, чаты, сетевые ИИ API и не отправляет текст автоматически.
- После копирования пользователь сам решает, куда вставлять содержимое. В инструкции могут быть текст страницы, классы, CSS, имена компонентов, пути файлов, фрагменты source hints и пользовательское пожелание.

## Webview и диагностика

- Локальная панель использует Content Security Policy и разрешает локальные ресурсы расширения.
- Обмен между страницей и webview выполняется через версионированный `postMessage` протокол с `sessionId`; сообщения проверяются по структуре и лимитам размера/количества.
- Канал **Design Studio Preview** предназначен для диагностики и записывает маршрут запроса, URL upstream, статус ответа и redirect metadata. При диагностике не публикуйте логи без проверки: query-параметры URL могут содержать данные вашего локального приложения.

## Граница доверия

Подключайте только собственный localhost dev-сервер и доверенный workspace. Preview исполняет HTML и JavaScript приложения внутри iframe, а для отображения может ослаблять некоторые HTTP-ограничения ответа приложения. Внешний ИИ-сервис получает данные только если пользователь сам вставит скопированный текст в этот сервис.

## Известные ограничения

- Service worker (`/__ds-sw.js`, scope `/`) регистрируется на временном origin preview host в исполняемых в iframe страницах. Он не кэширует ничего (`caches` API не используется) и при остановке preview-сервера остаётся зарегистрированным на уже неактивном порту; при следующем открытии расширение слушает новый временный порт, где регистрация повторяется. Явная вычистка `navigator.serviceWorker.unregister()`/`caches.delete()` при закрытии панели не реализована — известное ограничение.
- Ослабление response headers (`X-Frame-Options`, CSP) применяется только к ответам, отдаваемым через preview host (`/proxy/...` и `/project/...`). Прямые ответы dev-сервера в других контекстах не затрагиваются.
- WebSocket-проксирование поддерживает только `ws://` (не TLS) к loopback; `wss://` upstream не поддерживается.
