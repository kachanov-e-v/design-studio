# Current Stage

Preview host server shipped: the extension serves demo.html and an injected proxy for user dev apps over http://127.0.0.1 (PreviewHostServer), because vscode-resource subresource frames inside iframe-based webviews failed the ds:ping/ds:pong handshake ("Runtime not detected"). Root cause of runtime failing everywhere: preview-runtime bundle was built with --format=esm (invalid as a plain <script>); fixed to IIFE with global name DesignStudioRuntime, verified by verify-build. Inline demo runtime is regenerated by npm run build (inline:demo step). User-entered http(s) URLs are wrapped through the local proxy with <base>, root-absolute attribute/CSS rewriting, a service worker for JS-issued fetches, and a websocket tunnel for HMR. Protocol validated end-to-end in headless Chrome (handshake, ds:select on click, ds:apply-style) both for inline demo and proxied app without any user code changes. Automated checks pass: typecheck, lint, 113 tests, full build. Manual VS Code Extension Development Host verification remains.

Latest iteration (improvement backlog #3, Tailwind inline edits): the preview runtime detects Tailwind pages (cached scan for `--tw-` custom properties, CDN script markers, `window.tailwind`) and includes `classes` plus a `tailwind` flag in every element payload. On Tailwind pages Inspector style edits are translated to utility classes by `src/shared/tailwind.ts` (default 3/4 scales, palette color map, arbitrary values off-scale), applied live through the new `set-classes` op (full class list replacement, same-group conflicts removed), and journaled as pending kind `style` with the final class list + previous classes; the AI agent mirrors them in source. Untranslatable values fall back to raw-CSS editing. Protocol version stays "1" (additive fields only, optional).
